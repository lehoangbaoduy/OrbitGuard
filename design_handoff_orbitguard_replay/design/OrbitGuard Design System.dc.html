ORBITGUARD · REPLAY

Deep-space glass HUD — design system & component spec

One style: translucent glass panes over a near-black well, thin ice-white hairlines, and glow only on what is live. Status hues (red, amber, cyan, violet, green) are reserved for state — chrome is ice-white. Built on Nocturne (ground, neutral ramps, spacing, radii, focus ring) with type and accent overridden. Tokens live in orbitguard-tokens.css; the working screen is OrbitGuard Replay.

00

Before / after training — OrbitGuard Replay

Structure
  • A shared SCENARIO selector in the header (Normal · 3 simultaneous conjunctions · Capability reduction). Scenarios are sample episodes, not modes.
  • Two tabs: BEFORE TRAINING (untrained policy) and AFTER TRAINING (trained policy). Shield is ON in both, so the only difference is training. Both use the same layout and components; only the loaded source differs.
  • Switching tabs keeps the scenario, step, selected satellite, camera and play state; the strip values count to the new totals. Switching scenario jumps to that scenario’s start step. No side-by-side view.
Summary strip
  • Five cells — Total Δv · Maneuvers · Shield interventions · Collisions · Mission deviation — showing this tab’s episode total at 26 mono.
  • Under each value: a BEFORE and an AFTER bar on one shared scale (the active tab in ice, the other dimmed), so the gap reads without arithmetic. Then a ratio note (“65× after” / “98% less than before”) and the running value at the current step.
  • Phone: one row of five compact cells; values only, no bars.
  • It replaces the old key-metrics panel; the running values live in each cell’s “T+n” line.
Designing for both densities
  • This step: a 15-cell strip, one cell per satellite, showing the event or status glyph (always 15 cells, whatever the density), plus a tally (“◇ 11 ■ 0”). Status rows (◆ ○ ✕) stay individual. An event type with more than 3 satellites collapses to one group row, for example “◇ ×11 · S0 S1 S2 … · 11 blocked → COAST”. “Expand groups” or “+N more” drills down.
  • Timeline, Counts view: each lane is a histogram, with bar height = satellites with that event at that step (0–15). The shield lane uses a hollow bar with a solid cap, so it differs from maneuvers by shape as well as colour. Satellite-ID labels appear only when a lane has ≤30 runs (sparse AFTER); dense lanes show “peak 15/15 · T+67” instead.
  • Timeline, By satellite view: 15 rows × 360 steps, where tall cell = maneuver and short centred cell = shield. Click a row to inspect that satellite; click a column to jump to that step.
  • Scrubber: shield and maneuver density bars on two rows, plus amber ◆ ticks where a pair enters INSIDE d_safe or HIGH RISK. The hover preview lists counts first (“SHIELD ×11 · S0, S1 … +6”).
  • 3D cues (no rectangles, no strobing): each satellite is a small mesh3d model — a gold bus with two blue solar wings, drawn about 300× true size. Status is a pin on a stem above the model (◆ / ○ / ✕ plus an ID label); nominal satellites have no pin. MANEUVER is a green burn plume pointing along the exhaust of the approved intent (behind for RAISE / PH BACK, ahead for LOWER / PH FWD, downward for RADIAL). SHIELD is a thin violet ring around the satellite. A cue animates once, only when a run starts (ring settles 1.7×→1 in 600 ms; plume extends in 300 ms), and then holds still.
  • 3D labels: native Plotly scene.annotations — 12 px mono on a dark plate (90% void) with a coloured 1 px edge and a short leader to the pin. They show for flagged satellites, the selected one (ice edge) and all of them in label-mode “all”. Satellites within 1,100 km of each other merge into one plate (“S3 ○ ◇ · S11 ○ ◇”, max 4) instead of stacking. Labels are positioned by Plotly’s own projection, so the Dash port needs no overlay code.
  • Zoom: scroll or pinch while playing — wheel gestures use the same direct-update path as drag, so the camera isn’t reset. There are also − / + buttons next to Orbits / View.
  • Banner: names the satellites when there are 4 or fewer; otherwise “14 satellites”.
Shield OFF state
  • There are three independent choices: scenario × tab × SHIELD ON | OFF, which gives 12 recorded episodes. The shield control sits in the tab bar and defaults to ON. Switching it keeps scenario, tab and step.
  • A dashed, hatched indicator under the tabs reads “SHIELD OFF — nothing overrides the policy”, and the stage repeats it as a “SHIELD OFF” chip under the clock.
  • The Shield cell in the summary strip shows “—”, never 0. The legend’s shield items drop to 38% with a strikethrough and “(off)”. The timeline’s shield lane is hatched with the text “Shield off — no overrides recorded”. The step tally reads “◇ off”.
  • This step, empty: a dashed card listing “● All 15 satellites nominal / No maneuvers this step / ◇ No shield events — shield off”. With events present, a single dashed footer line keeps the off-state visible.
  • The remaining events keep colour + shape + label: ■ maneuver plume, ◆ / ○ status pins, ✕ collision (the capability scenario records one collision with the shield off, in both tabs).
  • Copy stays honest. The Collisions cell cites the reference runs (“10 runs: 1/10 · no action 1/10”), and nothing claims training makes the fleet safer. The visible difference is fuel and calm.
Fleet fuel gauge
  • 15 rows × 360 steps of remaining Δv, on a void → ice ramp (dark = empty, bright = full 2.0 m/s). Retired satellites tint red; thruster-offline rows are flat grey. It sits above the timeline in every state.
  • Readout: “0.00 / 30.0 m/s left · 15 of 15 tanks empty”, plus a sentence such as “Every tank is empty from T+38 min — later proposed burns change nothing.”
  • A click selects a satellite (row) and jumps to a step (column). The playhead moves by transform. In Dash it is one go.Heatmap (z = remaining_dv_mps.T).
Data source & playback
  • The UI reads a ReplaySource: meta, frameAt(t), summary and density[type][t]. Today it wraps a pre-recorded trace per (scenario, tab); a live feed can implement the same interface later. Nothing runs live in the UI.
  • Speeds: 1× / 2× / 4× / 8× (250 → 31 ms per step).
  • Previous / next event jumps to conjunction entries and Δv-budget depletions. Event-run starts are included only when sparse, because in BEFORE every step is an event.
  • Keys: Space = play/pause · ←/→ = step · [ / ] = previous / next event. Ignored while typing.

Colour-blind check: red vs green differ in lightness (L 0.70 vs 0.82) as well as shape; amber vs cyan differ in hue and shape (filled ◆ vs open ○); violet events are always open diamonds and halo the satellite rather than replacing it. Ratios are against the ground #161826; glass panes are lighter by <3%, so every pair stays above 4.5:1.

Component notes

Legend
✕ COLLIDED◆ HIGH RISK○ INSIDE d_safe● nominal
  • Always visible. Desktop: glass overlay at the stage’s bottom-left, three rows (Satellite / Event / Pair line + capability). Phone: a wrapping strip inside the sticky block.
  • Plotly’s legend stays off; this is html.Div, so it can show the dashed/dotted line samples and capability glyphs.
  • pointer-events: none — it never blocks camera drag.
Status chip
◆ HIGH RISK◇ SHIELD· nominal
  • Glyph + UPPERCASE label in mono 11 · padding 2/6 · radius 4 · fill status 14% · edge status 40%. Nominal has no fill and no edge, so it recedes.
  • Capability chips use a dashed neutral edge, never a status hue.
  • white-space: nowrap; the label is never truncated to the glyph alone.
Conjunction table
  • 4 columns that fit 390 px: Pair · Status chip · d_min (16 mono, d_safe beneath in 11) · Risk (value + 3 px bar, scaleX).
  • Order: collision → high risk → inside → nominal, then risk ↓, d_min ↑. Top 8 of the live pairs.
  • Collided pair: d_min “—” in red, sub-line “impact T+179”, risk “—”. Pairs with a retired satellite (not the collided pair itself) drop out of the ranking.
  • Rows involving the selected satellite render their pair ID in ice. Clicking a row selects the other satellite if one is already selected.
  • Built on Nocturne .table: fading row rules, hover tint.
Inspector
  • Placement: docked inside the 3D stage on the right, in a 330 px glass column under “Tracked this step”, whenever the stage is ≥780 px wide. The scene domain shrinks to 1 − 352/W, so Earth stays centred in the free area. Narrower than that it drops below the timeline, and on phone it becomes the Inspect tab.
  • One header line: ‹ S8 › stepper (30 mono, ice glow), status / event / capability chips, then three inline readouts on the right: Δv left (with a 2 px budget bar), mission deviation, and closest d_min with partner and d_safe.
  • A 15-cell selector strip (36 px desktop, 44 px phone): a live status glyph per cell and a ⊘/◐ corner mark. 3D clicks, table rows, timeline marks and rail rows select too.
  • One 210 px Plotly figure, three stacked rows sharing x: Δv (hv steps with ■/◇ marks), deviation, closest d_min vs dotted cyan d_safe (log).
  • A decision line under a hairline: this step’s proposed → approved (six intents: COAST, RAISE, LOWER, PH FWD, PH BACK, RADIAL), with a violet ◇ when the shield overrode it. Up to three “earlier” chips jump to those steps.
  • Retired: a red strip, “RETIRED · collided with S1 at T+179”.
Event timeline
  • Two views behind a Counts / By satellite toggle. Counts: three 42 px lanes (MANEUVER ■ / SHIELD ◇ / COLLISION ✕), where bar height is the number of satellites with that event per step (0–15). Shield bars are hollow with a solid cap, so they differ by shape too.
  • Only the selected satellite gets in-lane marks: a thin glowing line over its run plus a small “S9 ×3” in text-2. Runs within 24 steps merge, and marks closer than 18 steps are dropped, so labels never stack. Hover anywhere for the step’s satellite IDs.
  • By satellite: 15 rows × 360 steps, where tall cell = maneuver and short centred cell = shield. Click a row to inspect that satellite; click a column to jump to that step.
  • The lane header shows a running count over the total and the shield peak (“43 / 57 · peak 3”). With the shield OFF, the shield lane is hatched: “Shield off — no overrides recorded”.
  • Canvas in the prototype; in Dash it is go.Bar (Counts) and go.Heatmap (By satellite) with displayModeBar off. Only the playhead moves (transform).
Key metrics → summary strip
  • Key metrics live in the summary strip under the BEFORE / AFTER tabs (see 00). Each cell shows the episode total plus its running value at the current step (“T+250: 25.10”).
  • Values count to their new totals when the tab, scenario or shield setting changes (~420 ms). Collisions turn red once above 0. Shield interventions show “—” when the shield is off.
Playback controls
  • Controls left to right: ⏮ previous event · ‹ step · ▶ 54 px round play (glows while playing) · › step · ⏭ next event · scrubber · 1/2/4/8× segmented · Loop. On phone the scrubber moves to its own row, and speed becomes one cycling button.
  • Scrubber: density bars above the track (shield row, maneuver row) plus amber ◆ ticks at conjunction entries. Hover preview shows step, event counts with IDs, and pair-risk counts. Global keys: Space = play/pause, ←/→ = step, [ / ] = previous / next event. On the slider itself (role=slider): arrows ±1, Shift ±10, PgUp/PgDn ±30, Home/End, Space to play.
  • Dragging pauses playback and resumes it on release. Events do not pulse while scrubbing.
  • States: hover = ice 8% fill + hair-hi edge · active = scale .94 · focus-visible = Nocturne 2 px ice ring · disabled (no prev/next event) = 45%.
Empty & loading states
LOADING TRACE
  • Loading: the stage shows a hairline and “LOADING TRACE · episode.npz”, and panes keep their size (no layout jump).
  • No trace file: the stage reads “No episode loaded — pass --trace episode.npz”, and controls are disabled.
  • All nominal: the rail reads “● All 15 satellites nominal”.
  • Step 0: the inspector reads “Step 0 is the initial state — actions exist for steps 1–360”.
  • No actions for a satellite: “No actions proposed for S3 in this episode.” No collisions: the lane reads “No collisions in this episode”.

What Plotly’s 3D view can’t do — and the workaround

LimitationWorkaround (used in the prototype)
No label collision avoidance, leader lines or label backgroundsIn-scene text is the ID only (S8), and only for non-nominal or selected satellites. Status words live in the HTML “Tracked this step” rail.
No CSS glow, blur or bloom on WebGL markersA second marker trace at 24 px with rgba colour at 20% sits behind each non-nominal satellite.
Scatter3d ignores Plotly.animate transitions (no easing, no tween)A Dash clientside_callback drives a rAF loop that calls Plotly.react with interpolated positions and pulse sizes. Server callbacks are too slow above 1×.
Only 8 symbols: circle(-open), square(-open), diamond(-open), cross, xNo triangle, so HIGH RISK = diamond and the HTML glyph becomes ◆. Events are open halos so they don’t hide the status marker.
Opacity is per trace, not per point or segmentOne trace per status / event type, and fades apply to the whole trace. Ghosts use rgba colours instead of opacity.
No atmosphere shader or day/night textureEarth is a mesh3d sphere (64×128) whose vertexcolor is baked from day + night-lights maps (assets/earth-*-1k.jpg, shipped locally so it works offline), blended across the n·sun terminator and kept unlit. A 3.5%-larger shell at 9% opacity with fresnel 4 adds the rim, plus a faint graticule and orbit rings for scale. The stars are a CSS layer behind the transparent canvas, with parallax driven by the camera azimuth from plotly_relayouting. If the textures fail to load, it falls back to the stylised surface.
No public 3D→screen projection for HTML overlaysHTML overlays never track points. The collision flash is a stage-edge glow, and callouts sit in the rail.
Unstyled modebar; scroll-zoom hijacks the pageUse displayModeBar: false everywhere, with our own “Orbits” and “View” (reset camera via a uirevision bump) buttons. scrollZoom only on the stage.
Transparent surfaces z-sort badlyOnly one transparent surface (the shell), kept very faint. Earth stays opaque.
Hover isn’t available on touch and isn’t accessibleHover only repeats what the rail, table and inspector already show.
06

Porting to Dash

  1. assets/00_nocturne.css, 01_tokens.css, 02_og.css — Dash auto-loads them in order. Turn the prototype’s inline styles into .og-* classes in 02_og.css (pane, chip, kicker, btn-icon, scrub…).
  2. Serialise the trace once into dcc.Store: positions (float32, km), statuses / events as uint8, and the precomputed runs, ticks and metrics. That’s about 1.5 MB for N=15. It all derives from frame_at, so it works from a saved .npz with no ML.
  3. Keep step and playhead state client-side: one clientside_callback owns the rAF loop, the 3D Plotly.react, the scrubber and the playhead transforms. A dcc.Interval at 450 ms can’t feel continuous.
  4. Server callbacks only on step (throttled, or on pause) for the table, rail and inspector — or build them client-side too, which the prototype’s renderVals shows is cheap.
  5. Scrubber: dcc.Slider can carry marks, but not density bars or a hover preview. Use a small custom html.Div with a clientside pointer handler, or dash-extensions EventListener.
  6. Responsive: one CSS breakpoint at 760 px switches to sticky stage + tabs (dcc.Tabs styled as the tab strip). The desktop grid is flex-wrap 999:1, so the right column never leaves dead space and the stage grows to match it.
