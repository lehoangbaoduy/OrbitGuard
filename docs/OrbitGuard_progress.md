Per the master prompt: **pause and ask before assuming anything Astro-physics-related.** These are the concrete open items found while reading the PRD, batched here so they can be relayed to the astrophysics student in one pass rather than one at a time over multiple weeks:

1. **§39 numeric defaults are explicitly unvalidated** (§47.1: "my best guesses ... not validated physics") — needs sign-off or revision: position noise σ = 100 m, velocity noise σ = 0.1 m/s, `base_delta_v` = 0.1 m/s, hard-body radius = 5 m per satellite, `d_base`/`d_min`/`d_max` = 1000/200/5000 m, risk-proxy `z0`/`k` = 3.0/1.5.
2. **§9 ECI frame/epoch convention is unspecified — and this couples directly to constellation seeding.** PRD says only "must be documented in code" without naming one. The TLE-derived orbital elements in `data/TLE_snapshot_53deg_shell.csv` are TEME-referenced by origin (standard for TLE-derived mean elements). Astro needs to answer **both** parts together, not just "which frame the propagator uses": (a) EME2000/J2000 vs. a TEME-consistent internal frame, and the reference epoch convention, **and** (b) what conversion, if any, is applied when seeding satellite state from the CSV's TEME-origin elements into that chosen frame — otherwise the frame decision leaves the constellation generator (`P1-M5`) ambiguous even after §9 is nominally resolved.
3. **§23 RTN sign convention confirmation** — the mapping as written has `PHASE_FORWARD` = **−T** (retrograde) and `PHASE_BACKWARD` = **+T** (prograde), which reads inverted at first glance relative to the intuitive names. The PRD's own drift rationale (prograde burn → higher orbit → drifts *backward* relative to neighbors) explains it, but this needs explicit astro sign-off before coding `safety/maneuver_mapper.py`, not a silent "fix."
4. **§12 physics validation specifics** — which reference tool, Skyfield or poliastro (PRD lists both as options); what numerical tolerance counts as "agreed" for the propagator-vs-reference comparison; what J2 nodal-regression rate/direction is expected for the sanity check at this orbit's inclination/altitude.
5. **§32 shift-scenario #2 quantification** — "increased local density, N held fixed" is described qualitatively only. Needs a concrete physical definition (e.g., target spacing reduction factor, RAAN/phase clustering parameters) — PRD §44 Phase 5 explicitly assigns this definition to Astro.

**Phase 2 Part A additions (2026-09-27), same treatment as Q1-Q5 — implemented against a documented recommendation, not blocked on, per "Auto Mode" bias-to-proceed plus the same category as Q1 (the PRD itself frames these as fillable MVP placeholders, not hard blockers):**

6. **§22 `Sigma_norm,ij` (adaptive margin's normalized-uncertainty term) has no numeric definition beyond the symbol.** Implemented as `sigma_rel_m / d_base_m` (`safety/adaptive_margin.py::compute_sigma_norm`) — reuses the formula's own existing reference scale (`d_base`=1000m), stays dimensionless and O(1) for realistic uncertainties (~100-300m/1000m), needs no new config parameter. `sigma_rel_m` itself (§21's `g(Sigma_i,Sigma_j)`) is combined via standard independent-Gaussian quadrature, `sqrt(sigma_i^2+sigma_j^2)`, using each satellite's per-axis position sigma (`sensing/belief.py::combined_relative_sigma`) — this part is a standard statistical combination, not really a judgment call.

Target TCA is sampled Uniform(0.1×episode_horizon, 0.9×episode_horizon). All five constants are isolated at the top of the module for easy revision if the real astrophysics teammate disagrees.

If the actual astrophysics teammate reviews Q6-Q8 and disagrees, the affected code is isolated to `safety/adaptive_margin.py`'s `compute_sigma_norm` and the five named constants in `scenarios/conjunction_generator.py` — revisable without touching the leakage-boundary (`sensing/belief.py`) or `noise.py`.

**Phase 3 split additions (2026-09-30), same treatment as Q1-Q8 — implemented/frozen in the handoff test specs against a documented recommendation, not blocked on:**

9. **PRD §37 requires mission-deviation to be measured against expected orbital-element evolution, not a static t=0 reference — no code or numeric justification existed yet for why a static reference is actually wrong.** Empirically quantified before designing `physics/mission_deviation.py` (not yet implemented — Part A's own remaining work): an UNMANEUVERED satellite's J2 short-period oscillation alone swings semi-major axis by ~12,350m and eccentricity by ~0.0012 over one 6-hour episode (`episode_horizon_s`) — both *exceeding* §25's own stated tolerance bands (±2km on `a`, ±0.001 on `e`). A static t=0 comparison would flag a satellite that never maneuvered as having violated its own mission tolerance, which is nonsensical. `physics/mission_deviation.py` will therefore compare against a per-episode **no-maneuver shadow trajectory** (propagate the same initial state with zero applied Δv, alongside the real/maneuvered trajectory) rather than the t=0 osculating elements. This module is Part A's own future work, deliberately not implemented yet (implementation awaits go-ahead per the standing phase-gate workflow) — only its design is frozen here so Parts B/C's frozen interfaces (`own_mission_deviation` in `rl/observation.py`, `d_a/d_e/d_i/d_m` in `rl/reward.py`) have a stable contract to build against.
10. **PRD §24 leaves the neighbor-ranking tie-break, the "threatening" threshold, and the relative-geometry reference frame unspecified.** Frozen in `tests/rl/test_observation.py`: (a) ties in `risk_proxy` (which correctly and frequently underflows to exactly 0.0 for well-separated pairs, confirmed in the Phase 2 PR review) break by ascending `d_min_m`, never satellite index — index-based tie-breaking would leak persistent identity and violate §24's anonymity requirement; (b) `threatening_neighbor_count` (PRD's literal field name) uses `risk_proxy > 0.5` as the threshold, matching the risk formula's own `z0` crossover semantics, and is a **raw count** over *all* candidates (not just the top-k shown), not a fraction — a fraction over a variable-size pool would make "1 threat among 1 candidate" and "1 threat among 20" read identically as 1.0 vs 0.05 for the same underlying danger; (c) `NeighborCandidate.relative_position_m`/`relative_velocity_mps` are frozen as being in the **owning agent's own RTN frame** (via the already-frozen `physics.frames.eci_vector_to_rtn`), not raw ECI differences — computed upstream by Part A's future `rl/environment.py`. Raw-ECI relative vectors would vary with the observer's own orbital phase/plane for an otherwise-identical physical encounter, which would work against §24's explicit anonymity/generalization goal for the parameter-shared policy.
11. **PRD §24/§25 give no numeric normalization scales for the observation vector's real-valued fields.** Frozen in `tests/rl/test_observation.py` and re-exported as named constants any other Phase 3 module must import rather than redefine: `POSITION_SCALE_M = R_EARTH_EQUATORIAL_M`, `VELOCITY_SCALE_MPS = sqrt(mu/R_E)` (~7909.8 m/s circular-orbit reference speed), `RELATIVE_POSITION_SCALE_M = 5000.0` (= `d_max_m`), `RELATIVE_VELOCITY_SCALE_MPS = 1000.0`, `DELTA_V_BUDGET_SCALE_MPS = 2.0` (= `capability.remaining_delta_v_mps`), `MAX_DELTA_V_PER_ACTION_SCALE_MPS = 0.1` (= `maneuver.base_delta_v_mps`), `MINIMUM_SEPARATION_SCALE_M = 5000.0`. `own_mission_deviation` and `risk_proxy` are passed through unscaled since they already arrive pre-normalized/bounded. A dedicated frozen test (`test_normalization_constants_are_pinned_to_their_frozen_numeric_values`) pins these exact numbers, not just the self-consistent relationship between a constant and its own use — a self-consistency-only test would pass even if every scale were silently redefined to 1.0.
12. **PRD §25 states the reward formula's term structure but not each term's internal sign convention.** Frozen in `tests/rl/test_reward.py`: `R_safety` = the **minimum** (not mean) pairwise margin across all active neighbor pairs, clipped to `[-1, 1]`, defaulting to the clip-max (maximally safe) when there are zero active pairs — min, not mean, so one dangerous encounter can't be diluted by several benign ones; `R_mission = -D_mission` (explicit freeze — the PRD states `D_mission`'s formula but never states this sign; `compute_reward`'s top-level `+w2*R_mission` only makes sense if `R_mission` is already reward-signed); `compute_delta_v_term`/`compute_coordination_term` return **raw, non-negated** magnitudes (mirroring the PRD's literal formula, which explicitly subtracts both with `-w3`/`-w4` — pre-negating them a second time inside their own functions would double the sign). `own_mission_deviation` (§24, Q10 above) and reward.py's four mission-term components must be derived by Part A's environment from the *same* four raw deviation components and the *same* q-weights, so that `own_mission_deviation == -compute_mission_term(d_a,d_e,d_i,d_m)` holds by construction for the same satellite at the same instant — this equivalence is documented in both test files' module docstrings as a cross-module contract, since nothing else enforces it once B and C are implemented by different agents.
13. **PRD §25 explicitly says coordination-term "clipping/normalization must be fixed before training" without giving a formula — left genuinely open, not silently resolved.** `compute_coordination_term` in `tests/rl/test_reward.py` returns the raw, unclipped positive risk degradation (`max(0, total_risk_post - total_risk_pre)`). With N=15 there are up to 105 active pairs, so this could dominate the other three (bounded, O(1)) reward terms once real numbers are plugged in. This is intentionally left as an **open Q-item owned by Part C's own reward-weight grid search** (PRD §39/§48) rather than resolved here — Part C should not invent a normalization silently inside `compute_coordination_term` itself; any scaling decided later belongs in `compute_reward`'s `w4` weight or a documented follow-up parameter, so it stays visible and tunable, not buried.

**Part A `rl/environment.py` implementation additions (2026-09-30), resolved while wiring the per-control-step pipeline together — implemented against a documented recommendation, not blocked on, per the user's explicit "proceed with Part A" go-ahead:**

14. **Should the reward's mission term (and `own_mission_deviation`) use ground truth or belief?** The simulator always has ground truth available, but PRD §14's leakage-boundary philosophy reserves it for collision determination/final metrics only (§14 point 5). Resolved: **both use belief**, preserving the frozen `own_mission_deviation == -compute_mission_term(...)` equivalence (Q12) exactly, by computing `physics.mission_deviation.compute_mission_deviation` from the post-step belief against a deterministically-evolved shadow belief (both propagated from the *same* one-time noisy snapshot taken at `reset()`, never re-noised). **Empirically quantified cost of this choice** (not previously measured): under an all-`NO_MANEUVER` N=2 episode, `own_mission_deviation` grows from ~0.04-0.09 at control step 1 to ~0.35 at step 360 (end of a 6h episode) purely from the shadow belief's own initial noise realization drifting apart from the (also noisy) live belief — there is no actual mission deviation happening, only measurement noise compounding over 6 hours of free propagation. This means `own_mission_deviation`/`R_mission` carry a real, time-growing noise floor that is NOT a property of the satellite's actual behavior; Part C's reward-weight tuning (Q13) should be aware `R_mission` is not zero-mean-stationary across an episode even for a perfectly on-mission satellite.
15. **Ground-truth collision detection: check only the two 60s control-step endpoints, or the full fine-grained window?** At ~2km/s relative velocity, a satellite can travel ~120km within one 60s control step — endpoint-only checks would miss essentially all real collisions. Resolved: `rl/environment.py` propagates ground truth at `physics_dt_s=10s` resolution across the full `control_dt_s=60s` step (6 substeps) and runs `conjunction.collision.detect_collision` over that entire fine-grained trajectory window, not just the two endpoints.
16. **Predicted (belief-based) conjunction assessment: what lookahead window, and what frame/timing for `NeighborCandidate`'s relative geometry?** Resolved in the new `rl/conjunction_assessment.py`: `assess_all_pairs` predicts every belief `lookahead_s=1800s` (30 min) forward via `predict_belief`, then runs TCA/risk/adaptive-margin on the predicted trajectories; `build_neighbor_candidates`'s relative position/velocity are taken at the **current instant** (not projected to the predicted TCA) and expressed in the observing agent's **own current RTN frame** — the raw "what does my neighbor look like right now" perceptual input, with `d_min_m`/`risk_proxy` separately carrying the forward-looking predicted threat (consistent with Q10's RTN-frame freeze).
17. **Local-density midpoint for the adaptive margin (Q7): computed from which positions, at what time?** Resolved: current-instant belief positions (same instant as the pair's own screening), consistent with Q7's original resolution that density must use belief, never ground truth, positions.
18. **R_safety (and the coordination term's "post" value): computed from a conjunction assessment taken before or after the agents' actions are applied?** Resolved via a causally-ordered pipeline: the assessment computed at the *start* of a control step (before actions) is that step's "pre" value, feeding both that step's observations and (saved for next step) the reward's coordination baseline; a *second* assessment computed immediately after the physical control step (post-maneuver, post-propagation) is both that step's reward "post" value (feeding `R_safety` and the coordination term) AND the *next* step's "pre" — i.e., consecutive steps' assessments chain directly, with reward computed as a function of the (pre, action, post) transition, matching standard RL semantics.
19. **Coordination term's global "pre"/"post" risk (Q13's `total_risk_pre`/`total_risk_post`): summed over which assessment set?** Resolved: summed over all `PairAssessment.risk_proxy` values across the *entire* candidate-pair set (not per-agent), from the same pre/post assessment pair described in Q18 — a single shared scalar term applied identically to every agent's reward that step, matching PRD §25's description of coordination as a *global* term.
20. **Capability enforcement (checklist #15, "NO_MANEUVER never an automatic fallback"): how do `maneuver_enabled=False` and an insufficient `remaining_delta_v_mps` budget interact with the chosen action?** Resolved in `rl/environment.py::_apply_actions`: `maneuver_enabled=False` zeroes the applied delta-v entirely regardless of the chosen intent (the satellite physically cannot maneuver); an enabled-but-insufficient budget **caps the applied magnitude** at `remaining_delta_v_mps` (direction preserved from the proposed delta-v) rather than silently substituting `NO_MANEUVER` — a partial burn in the intended direction is always closer to the agent's actual intent than doing nothing. `max_delta_v_per_action_mps` is passed directly as `map_intent_to_delta_v`'s `base_delta_v_mps` parameter, naturally tying per-action magnitude to the satellite's own capability.
